# Архітектура

## Архітектурний стиль
Проєкт використовує багатошарову архітектуру:
- `controllers` приймають HTTP-запити й повертають відповіді API;
- `services` містять бізнес-логіку та сценарії використання;
- `repositories` ізолюють роботу з persistence-шаром;
- `models` описують доменні сутності;
- `dto` задають контракти запитів і відповідей;
- `db` і `core` містять інфраструктурні залежності та конфігурацію;
- `utils` містять допоміжні стратегії та дрібні інструменти без HTTP- або DB-залежностей.

Такий поділ дає змогу тестувати бізнес-логіку окремо від API і зменшує зв’язність між веб-шаром та сховищем даних.

## Чому MongoDB
Для дошки оголошень MongoDB підходить з практичних причин:
- оголошення, повідомлення й галереї природно моделюються документами;
- схему можна еволюціонувати без важких SQL-міграцій;
- фільтрація, сортування і швидке розширення каталогу добре лягають на документну модель;
- `mongomock` дає змогу зберегти швидкі й детерміновані інтеграційні тести без зовнішньої БД у CI.

### Repository

- [base.py](../../src/repositories/base.py)
- [listing_repository.py](../../src/repositories/listing_repository.py)
- [user_repository.py](../../src/repositories/user_repository.py)

Репозиторії ізолюють persistence-операції від сервісного шару. Сервіси працюють із доменними сутностями та методами репозиторіїв, а не з raw `pymongo` calls.

### Strategy
Файл:
- [listing_sort_strategy.py](../../src/utils/listing_sort_strategy.py)

Стратегія використовується для перемикання алгоритму сортування каталогу (`created_at` / `price`, `asc` / `desc`) без розростання умовної логіки всередині репозиторію.

### Factory
Файл:
- [client_factory.py](../../src/db/client_factory.py)

Створення клієнта БД винесене в окрему фабрику. Вона вибирає між реальним `MongoClient` і `mongomock`, що спрощує тестування та централізує infrastructure setup.

## SOLID
- `SRP`: контролери, сервіси, репозиторії та DB-фабрика мають окремі відповідальності.
- `OCP`: нові сценарії можна додавати через нові сервіси, репозиторії або стратегії без зламу наявних API-контрактів.
- `LSP`: сервіси працюють із абстрактним репозиторним шаром і доменними сутностями, а не з HTTP- або Mongo-специфічними деталями.
- `ISP`: залежності вузькі; немає одного “бог-об’єкта”, через який проходять усі обов’язки.
- `DIP`: верхні шари залежать від repository/service boundaries і factory abstraction, а не від деталей створення клієнта БД.

## Тестованість
- unit-тести перевіряють DTO, security helpers, сервіси та архітектурні патерни;
- integration-тести перевіряють REST API поверх `mongomock`;
- CI генерує XML та HTML reports для coverage і test results;
- Sonar-конфіг використовує ті самі артефакти для Quality Gate.

## Переваги поточного підходу
- швидкий локальний запуск;
- ізоляція бізнес-логіки від веб-шару;
- придатність до статичного аналізу та coverage-driven розробки;
- готовність до подальшого рефакторингу в більш виражену ports/adapters або hexagonal модель.
