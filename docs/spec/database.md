# Проєктування бази даних

## 1. Обрана технологія
Проєкт використовує `MongoDB` як основне сховище даних.

Причини вибору:
- природна відповідність документної моделі до оголошень і повідомлень;
- простіше еволюціонувати схему;
- зручно працювати з вкладеними або пов’язаними даними;
- швидкий локальний запуск;
- можливість тестування через `mongomock`.

## 2. Колекції
### `users`
Зберігає користувачів платформи.

Основні поля:
- `id`
- `email`
- `full_name`
- `password_hash`
- `role`
- `is_blocked`
- `created_at`

### `categories`
Зберігає категорії каталогу.

Основні поля:
- `id`
- `name`
- `description`

### `listings`
Зберігає оголошення.

Основні поля:
- `id`
- `title`
- `description`
- `price`
- `status`
- `rejection_reason`
- `owner_id`
- `category_id`
- `created_at`
- `updated_at`

### `listing_images`
Зберігає прив’язані зображення до оголошень.

Основні поля:
- `id`
- `listing_id`
- `url`
- `position`

### `messages`
Зберігає повідомлення між користувачами.

Основні поля:
- `id`
- `listing_id`
- `sender_id`
- `recipient_id`
- `body`
- `created_at`

### `counters`
Службова колекція для видачі integer `id`, щоб зовнішній API не залежав від Mongo ObjectId.

## 3. Причина використання numeric id
Хоч MongoDB нативно працює з `_id`, поточний API зберігає прості числові `id`, тому що:
- це простіше для DTO;
- це стабільніше для frontend;
- легше читати дані в тестах;
- зручно для документації та демонстрації.

Колекція `counters` зберігає значення лічильників для кожної предметної колекції.

## 4. Індекси
Під час ініціалізації створюються індекси:
- `users.email` — `unique`
- `categories.name` — `unique`
- `listings(status, created_at)` — для каталогу та модерації
- `listing_images(listing_id, position)` — для побудови галереї
- `messages(listing_id, created_at)` — для історії повідомлень

## 5. Цілісність даних
MongoDB не нав’язує жорсткі foreign keys, тому цілісність забезпечується на рівні:
- сервісного шару;
- репозиторіїв;
- бізнес-правил;
- DTO-валідації.

Наприклад:
- не можна створити оголошення з неіснуючою категорією;
- не можна видалити категорію, яка використовується оголошеннями;
- не можна надіслати повідомлення самому собі;
- не можна публікувати оголошення від заблокованого користувача.

## 6. Зв’язки між сутностями
- один `User` може мати багато `Listing`
- одна `Category` може містити багато `Listing`
- один `Listing` може мати багато `ListingImage`
- один `Listing` може мати багато `Message`
- один `User` може бути і `sender`, і `recipient` у багатьох `Message`

## 7. Нормалізація в документній моделі
Модель обрана як компроміс між нормалізацією та зручністю:
- основні сутності зберігаються в окремих колекціях;
- зображення винесені окремо в `listing_images`, а не вбудовані в `listings`;
- повідомлення зберігаються окремо, щоб не роздувати документи оголошень.

## 8. Тестування persistence-шару
У тестах використовується `mongomock`, що дає:
- швидкий unit/integration прогін;
- відсутність залежності від зовнішнього Mongo-сервера;
- відтворюваність у CI.
