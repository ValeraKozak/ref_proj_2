# Вимоги до проєкту

## 1. Загальна інформація
**Назва проєкту:** Платформа для дошки оголошень  
**Предметна область:** веб-платформа для публікації, модерації та перегляду оголошень з можливістю обміну повідомленнями між користувачами.

Проєкт призначений для демонстрації повного циклу backend/frontend розробки:
- формалізація вимог;
- моделювання системи;
- побудова REST API;
- реалізація бізнес-логіки;
- тестування;
- CI/CD;
- контроль якості через SonarCloud.

## 2. Проблема, яку вирішує система
У типових сценаріях купівлі, продажу та обміну користувачам потрібен простий цифровий майданчик, де можна:
- розміщувати власні оголошення;
- швидко знаходити потрібні товари чи послуги;
- комунікувати безпосередньо з автором оголошення;
- бути впевненими, що контент проходить контроль якості.

Без централізованої системи користувачі стикаються з такими проблемами:
- відсутність структури даних і категорій;
- змішування якісного та низькоякісного контенту;
- відсутність контрольованої модерації;
- незручна комунікація між сторонами;
- ризики дублювання, спаму або неправдивих публікацій.

Платформа дошки оголошень вирішує ці проблеми через:
- керовану модель оголошень;
- категоризацію;
- пошук, фільтрацію та сортування;
- модерацію перед публікацією;
- обмін повідомленнями в межах платформи;
- рольову модель доступу.

## 3. Цільова аудиторія
### Гість
Користувач без авторизації, який може переглядати каталог, відкривати сторінки оголошень і знайомитися зі структурою сервісу.

### Зареєстрований користувач
Користувач, який:
- створює власні оголошення;
- редагує або архівує їх;
- переглядає власний кабінет;
- надсилає повідомлення авторам інших оголошень;
- працює з галереєю зображень.

### Модератор
Користувач із розширеними правами, який:
- переглядає чергу оголошень на модерацію;
- схвалює або відхиляє оголошення;
- фіксує причину відхилення;
- контролює якість публікацій перед появою в публічному каталозі.

### Адміністратор
Користувач із повними правами, який:
- керує категоріями;
- переглядає й змінює користувачів;
- блокує порушників;
- має всі права модератора;
- керує операційною частиною системи.

## 4. Функціональні вимоги
### 4.1 Автентифікація та користувачі
Система повинна дозволяти:
- реєстрацію користувача за email, іменем та паролем;
- вхід через JWT;
- перегляд власного профілю;
- редагування власних даних;
- адміністрування користувачів з боку адміністратора;
- блокування користувача для обмеження його можливостей.

### 4.2 Оголошення
Система повинна підтримувати:
- створення нового оголошення;
- редагування оголошення власником;
- архівацію оголошення;
- перегляд публічних оголошень;
- перегляд списку власних оголошень;
- перегляд детальної сторінки конкретного оголошення.

### 4.3 Категорії
Система повинна підтримувати:
- створення категорій;
- перегляд списку категорій;
- редагування категорій;
- видалення категорій з перевіркою зв’язків.

### 4.4 Модерація
Система повинна забезпечувати:
- постановку нових оголошень у статус `pending`;
- схвалення оголошення модератором або адміністратором;
- відхилення оголошення з причиною;
- відображення черги оголошень на модерацію.

### 4.5 Повідомлення
Система повинна дозволяти:
- надсилати повідомлення автору оголошення;
- переглядати власні повідомлення;
- відкривати окреме повідомлення;
- видаляти власні повідомлення.

### 4.6 Завантаження зображень
Система повинна підтримувати:
- завантаження декількох зображень за один запит;
- перевірку дозволених MIME-типів;
- контроль максимального розміру файлу;
- формування URL для подальшого відображення у frontend.

### 4.7 Пошук і каталог
Публічний каталог повинен підтримувати:
- текстовий пошук;
- фільтрацію за категорією;
- фільтрацію за мінімальною та максимальною ціною;
- сортування за датою створення;
- сортування за ціною;
- перегляд карток оголошень і детальної сторінки.

## 5. Нефункціональні вимоги
### 5.1 Продуктивність
- API має повертати відповіді в прийнятний час для CRUD-операцій.
- Пошук і фільтрація мають спиратися на індекси в БД.
- Каталог має коректно працювати при великій кількості оголошень.

### 5.2 Безпека
- JWT-автентифікація для захищених маршрутів.
- Обмеження доступу за ролями.
- Валідація вхідних DTO.
- Відсутність хардкоджених продакшн-секретів у коді.
- Контроль upload-сценаріїв.

### 5.3 Якість коду
- розділення на логічні шари;
- покриття тестами;
- lint/static analysis;
- Sonar Quality Gate;
- документація та діаграми.

### 5.4 Надійність
- стабільна робота локально та через Docker;
- відтворювані CI/CD-перевірки;
- детерміновані тести без залежності від зовнішнього продакшн-середовища.

## 6. Ролі та права доступу
| Роль | Основні дії |
|---|---|
| `guest` | Перегляд каталогу, категорій, детальної сторінки |
| `user` | Створення/редагування/архівація власних оголошень, повідомлення |
| `moderator` | Черга модерації, схвалення та відхилення оголошень |
| `admin` | Усі права модератора, плюс керування категоріями і користувачами |

## 7. Основні сценарії використання
1. **Реєстрація нового користувача**  
   Користувач вводить email, ім’я та пароль, після чого система створює новий акаунт.

2. **Авторизація та отримання токена**  
   Користувач входить у систему й отримує JWT для захищених операцій.

3. **Створення нового оголошення**  
   Авторизований користувач створює оголошення, яке потрапляє в статус `pending`.

4. **Модерація оголошення**  
   Модератор або адміністратор перевіряє оголошення, схвалює його або відхиляє з причиною.

5. **Пошук оголошення в каталозі**  
   Гість або авторизований користувач використовує текстовий пошук, категорії, ціну та сортування.

6. **Надсилання повідомлення автору**  
   Користувач відкриває картку оголошення й надсилає повідомлення його автору.

7. **Керування категоріями**  
   Адміністратор створює, редагує або видаляє категорії для підтримки структури каталогу.
